6. SEGURIDAD — HALLAZGOS
================================================================================

6.1 Lo que está BIEN:

  ✓ Sin servidor HTTP propio (no hay puertos abiertos; solo conexiones
    salientes para: modelos.dev, git remoto, webhooks salientes, ping).
  ✓ Sin eval()/exec()/os.system()/pickle.load en el código Python
    (los `exec()` detectados son el bucle de eventos Qt, no Python exec).
  ✓ Escritura atómica del registro (temporal + os.replace): un corte de luz
    no lo deja corrupto; si se corrompe, no arranca en vez de perder datos
    (copia .corrupto, nunca pisa una anterior).
  ✓ _sanitizar() en webhooks enmascara tokens (telegram, whatsapp, discord)
    antes de emitir errores — evita que tokens aparezcan en logs/UI.
  ✓ gitignore excluye el framework del repo del usuario (plan.md,
    progreso.log, gate_checks/ no se commitean al repo del usuario).
  ✓ El gate restaura gate.sh/gate_checks prístinos si el agente los alteró
    (gate_intacto/restaurar_gate) — previene inyección de código vía agente.
  ✓ Límite térmico CPU con auto-apagado (seguridad del hardware).
  ✓ CI ejecuta ruff + 264 tests en cada push/PR.

6.2 Lo que NO está (riesgos reales):

  ✗ Tokens de webhooks (telegram_token, whatsapp_token, discord_webhook_url)
    se guardan en CLARO en ~/.config/autopiloto/proyectos.json.
    Permisos del fichero: 664 (rw-rw-r--) — legible por grupo.
    → Recomendación: os.chmod 0o600 al escribir; idealmente usar
      keyring/libsecret (aunque es plataforma-dependiente).
    → Estado actual: el registro de esta máquina NO tiene tokens (0
      coincidencias), así que no hay fuga activa, pero el hueco existe.

  ✗ Sin secret scanning en CI. github_run_secret_scanning existe como
    herramienta manual pero no está en el workflow.

  ✗ Sin auditoría de dependencias (pip-audit / safety) en CI.

  ✗ Dependencias sin hash-pinning (pinned solo en pyproject con >=).

  ✗ El agente IA (opencode/claude/codex) corre con el usuario completo:
    lee/escribe/ejecuta en el proyecto SIN sandbox (Docker/gVisor).
    Es inherentemente el modelo de la herramienta, pero no está documentado
    como riesgo para el usuario final.

  ✗ Credenciales de los agentes en ~/.config/... — fuera de nuestro control
    pero afecta a la superficie total.

  ✗ Sin SBOM ni firma de releases (no hay releases).

  ✗ QMessageBox del registro corrupto muestra la ruta del fichero —
    informativo, sin datos sensibles.
